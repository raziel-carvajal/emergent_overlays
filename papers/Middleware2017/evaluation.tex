%

In particular, we are interested in finding answers to the following research questions:

\subsection{Simulation Environment}
\labsection{simulation-env}

Our experiments are inspired by the scenario of a crowd of humans carrying portable communication devices (e.g., phones) in an area with no infrastructure connectivity.
%
In this area, there are several points of interest where people tend to stay.
%
As a result, the density of devices in the points of interest is high, and the mobility is low.
%
Meanwhile, fewer nodes constantly move in the area between point of interests. 
%
The dissemination of information from one individual to all the others is critical, and uses ad-hoc connections between devices.
%
Our evaluation of broadcast algorithms for MANETs is mainly driven by two factors: \emph{network density} and \emph{nodes mobility}.
%
We describe in the following the parameters used in our study.

\smallskip
\noindent
\textbf{Simulator.}
We rely on OMNET++4.6/INET3.3, a simulation framework for the evaluation of networking algorithms~\cite{Varga:2008:OOS:1416222.1416290}.
%
This tool provides a full implementation of the IEEE 802.11g standard.
%
In addition, it contains models for the mobility of nodes and for energy consumption.


\smallskip
\noindent
\textbf{Energy Model.}
This metric depends on the wireless communication chip used.
%
We model power consumption using the specifications of a commercial chip found in modern mobile devices.
%
We use Broadcom BCM4329 chip~\cite{BCM4329}, which supports Wi-Fi 802.11g on the 2.4 GHz frequency band.

\smallskip
\noindent
\textbf{Communication Scenario.}
%\subsection*{Communication Scenario}
Simulated participants use their devices to broadcast messages without external coordination and may attempt to do so at nearly the same time.
%
We set our experiments to perform 200 broadcast messages.
The frequency between broadcasts is $0.1$s.
%
The source of each message is randomly selected.
%
The content of each message is randomly generated, unique and with a length of 32~Bytes. 
%

\smallskip
\noindent
\textbf{Simulation time.}
As mentioned in~\refsection{mechanism}, some algorithms need to build a topology.
%
To guarantee that the first broadcast message is properly handled by all protocols, we set an initial warm-up period of 2s, allowing CDS-based algorithms to perform this initial construction.
%
The total simulation time is then $4 + {\delta t} \times M$, where ${\delta t}$ is the interval between broadcast messages and $M$ is the number of scheduled messages.


\smallskip
\noindent
\textbf{Mobility Model.}
%\subsection*{Mobility}
We use a mobility model with points of interest (PoI) proposed by Piorkowski et al.~\cite{mobility_density_model}.
%
In this model, all nodes move in short steps that are defined using two Gaussian distributions.
%
To do so, nodes are classified in two groups: nodes in the ``vecinity'' of a PoI use a distribution $\mathcal{N}(0, \sigma_1^{2})$, and nodes in between PoIs use $\mathcal{N}(0, \sigma_2^{2})$ where $\sigma_1 <  \sigma_2$.
%
As a consequence, nodes in the ``vecinity'' of a PoI move slower than nodes in between PoIs.
%
The use of these distributions also cause that often nodes stay most of the time in a PoI; as result, the density in PoI is high while it is low elsewhere.

To generate the traces, the mobility model checks, during each step, the current position of a node to see whether it is in the ``vicinity'' of a PoI.
%
Depending on that, it selects the distribution to use to move the node.
%
Finally, the initial position of each node is selected using a uniform distribution. 
%
The exact configuration we use for each parameter is shown in~\reftab{mobility}.

\smallskip
\noindent
\textbf{Algorithm-specific parameters.}
%\subsection*{Algorithm-specific parameters}
The behavior of each protocol depends on its parameters, for which we favor values previously reported in the literature.
%
For instance, we use 1.5s as the \emph{hello time} for \emph{MPR}.
%
In the case of \emph{ABBA}, we use 60 milleseconds as the maximum waiting time.
%

For adaptive approaches, we only allow switching between two protocols.
%
At the beginning of the simulation, each nodes is executing \textit{simple flooding}.
%
Afterwards, a node is free to change its protocol based on some policy.
%
However, it can only change back and forth between \textit{simple flooding} and \textit{MPR}.
%
We are selecting these two algorithms based on previous studies that show their benefit in the scenarios we are considering~\cite{DensityMobDrivenEval}.  
%

\subsection{Evaluation metrics}

To properly compare our approach against previous solutions, we present the results of our experiments in terms of a set of well-established metrics:


\noindent $\triangleright$
\textbf{Coverage} --
the percentage of nodes that successfully receive a broadcast message at least once.
%
Since we are executing many broadcast session, we are interested in the evolution of this metric over time.

%
\noindent $\triangleright$
\textbf{Saved Rebroadcasts (SRE)} --
the number of forwarding we avoid by using a given algorithm instead of \emph{simple flooding}.
%
To compute the SRE of one algorithm $A$ in a network of $N$ nodes, we measure the number $R_m$ of retransmissions made by $A$ to disseminate a message $m$. The $ \textit{SRE}_m$ for message $m$ is then $N - R_m$.
%
Since in our experiments we are disseminating many messages, we compute the mean \emph{SRE} and use it as metric for our comparison study.
%
This metric is useful to assess the performance of algorithms in terms of both network and energy usage.

%\noindent $\triangleright$
%\textbf{Duplicate messages} --
%the number of times one broadcast message is received again after its first reception.
%


\noindent $\triangleright$
\textbf{Broadcast time} --
the time to disseminate a message with a Coverage of 100\%.
%
We are interested in knowing how long does it take to deliver a message because this helps to understand what kind of use cases can be solved using a given algorithm.
%
For instance, some applications can tolerate high-latencies while others need instead response.


% 
\noindent $\triangleright$
\textbf{Energy consumption} --
the energy consumed by nodes for the broadcast of all messages and, when applicable, for the construction and maintenance of the overlay.

\reffigure{coverage} shows the coverage obtained when different algorithms are used to disseminate messages in MANET.
%
In particular, it depicts the results for previous approaches such as \textit{ABBA}, \textit{MPR}, \textit{simple flooding} and our adaptive solution.
%
The first thing to notice is that this network is often disconnected, for that reason the coverage is less than 100\% for many broadcast sessions.
%
The second interesting point is that our adaptive solutions outperform both \textit{ABBA} and \textit{MPR}.
%
In fact, the adaptive approach often follows the same trend as \textit{flooding}.
%
However, this pattern does not occur during two ranges of broadcast sessions: before session 50, and short after session 100.
%
In both cases, this happens because some nodes have switched from \textit{flooding} to \textit{MPR}, but \textit{MPR} is still warming up and the node is not acting a relay when it should be doing so.
%
Finally, the adaptation policy has little effect in terms of coverage.
Indeed, although in a few broadcast session the \textit{local} policy behaves better than \textit{SWSP}, the difference is negligible.
