\section{Experimental Scenario}
\label{sec:scenarios}

%
Our experiments are inspired by a real life scenario: a physical \emph{demonstration} where the infrastructure for mobile communication is not able to serve the amount of clients and where individuals use their mobile phones in an ad-hoc mode to communicate.
%
In this scenario, the efficient dissemination of some messages to all participants is critical.
%
To simulate this kind of scenario, we consider two parameters that influence the performance of broadcast in MANETs: \textit{network density} and \textit{nodes mobility}.
%
In the following, we describe the simulation environment and the parameters used in our study.

%\subsection*{Simulation tool}
\noindent
\textbf{Simulation tool.}
For our performance comparison study, we rely on INET3.3/OMNET++4.6, a simulation framework specifically aimed at evaluating networking algorithms~\cite{Varga:2008:OOS:1416222.1416290}.
%
This tool provides models for many protocols of the network stack such as 802.11g.
%
In addition, it can model aspects such as mobility and energy consumption aspects.

\noindent
\textbf{Communication Scenario.}
%\subsection*{Communication Scenario}
In a \textit{demonstration} scenario, some attendees have mobile devices with IEEE 802.11 capability.
%
Participants use such devices to broadcast messages using a MANET and they might attempt to do so at nearly the same time.
%
The messages to broadcast are usually \textit{short} because most of them are generated using the input capabilities of mobile devices.
%
To simulate these conditions,  we set the number of broadcast messages to \nrMessages{} and the interval between messages to $0.5$ seconds in our experiments.
%
In addition, the source of each message is randomly selected during the generation of the network (see next subsection).
%
Finally, the content of each message is randomly generated, unique and with a length of 32 bytes at most. 
%
%These two values allow us to evaluate the protocols under heavy and light network load.
%

\noindent
\textbf{Node Density.}
%\subsection*{Node Density}
We are interested in generating scenarios with different node density; this allows us to simulate more accurately the \textit{demonstration} use case.
%
%In particular, the density in the vicinity of each node must equal a given value plus/minus a threshold.
%
To characterize the node density, we use three parameters: transmission range, map size and number of nodes.
%
As shown in~\cite{Penrose2003}, there is a dependency between these parameters that  allows us to build network topologies with a given density by using random geometric graphs.
%
In our experiments, all nodes have a transmission range of 20~meters.~\footnote{Theoretically, IEEE 802.11 allows communication in a range between 20 and 140 meters, depending on the line of sight.
Previous empirical tests show that it can be between 20 and 30 m in indoor or crowded places~\cite{Garbinato2010}.}
Meanwhile the number of nodes is fixed to \nodesNumber{}, the mode reported by previous studies on the size of demonstrations in Western Europe~\cite{kriesi1995new}.
%
To create a network with a given density, we use the values of transmission range and number of node to compute the map size \deleted{using the aforementioned dependency relationship}.
%
Then, we generate a laying on the map by using a procedure based on random geometric graphs.
%
The output of this procedure is a network topology with the desired density.
%
%
\deleted{Table~\ref{tbl:densisty-parameters} summarizes the simulations parameters we use to configure the density.}
%
We instantiate \densitiesNumber{} networks of \nodesNumber{} nodes each and set the densities to  {5,10, \dots, 35, 40}; a range of values that is frequently found in the literature.
%
This leads to a maximum map size of $354 \times 354$ while the minimum map is $125 \times 125$.


\noindent
\textbf{Mobility.}
%\subsection*{Mobility}
In our evaluation, we use the \textit{truncated-levy walk} (LW) mobility model, as it characterizes the mobility traces of humans carrying wireless devices~\cite{Rhee:2011}.
%
This model generates traces composed of frequent short walks and occasional rides to distant locations.
%
In our experiments, we define two kind of scenarios: one without mobility (\textit{static}) and another with mobility at walking speed (\textit{dynamic}).
%
The generation of \textit{static} scenarios was presented in the previous subsection.
%
To generate \textit{dynamic} scenarios, we begin with a \textit{static one}.
%
Then, we use the LW model to generate mobility traces for each node.
%
The parameters of the LW model are set in such a way that the average node speed is close to $1.4$ $m/s$ -- an estimation of the preferred walking speed~\cite{Browning390}.
%
\deleted{To do so, we use the following values to feed the mobility model:}

\noindent
\textbf{Energy Consumption.}
%\subsection*{Energy Consumption}
The power consumption must be considered in evaluating protocols that use wireless communication.
%
Since this metric depends on the Wi-Fi chip used \deleted{by mobile devices}, we model power consumption using the specifications of an actual chip found in modern mobile devices.
%
The Broadcom BCM4329~\cite{BCM4329}, which supports Wi-Fi 802.11g on the 2.4 GHz frequency band, is installed in many modern devices.
%
Its consumption in different operation modes follows: \textit{sleep} (648 nW), listen (244.8 mW), receive (295.2 mW), transmit (1206 mW).
%
This information is used in setting the power consumption model of INET.

To simulate this chip, we use the \textit{StateBasedEnergyConsumer} model provided by INET.
%
This model measures how many Joules were consumed based on the time the chip spends on each mode (as described in Table~\ref{tbl:wifi-chip}).
}
%
\deleted{Formally, this energy consumption model uses three functions: $c : M \mapsto \mathbb{R} $, $r_m: \mathbb{R} \mapsto M$ and $t_m: \mathbb{R} \mapsto M$ where $M$ is the set of operation modes of the chip, $c$ is the consumption of the chip on each mode, and functions $r_m, t_m$ map from simulation time to operation modes of the \textit{receiver} and \textit{transceiver}, respectively.
%
INET then computes the energy consumption $C(t)$ using:  $C(t)=\int_{0}^{t_\textit{simulation}} (r_m \circ c) (t) + (t_m \circ c) (t) \textit{dt}$.
%
The function $m$ is given and INET computes both $r_m$ and $t_m$ during the simulation.}


\noindent
\textbf{Algorithm-specific parameters.}
%\subsection*{Algorithm specific parameters}
The behavior of each protocol depends on the values of its parameters.
%
To configure these parameters meaningfully, we choose values previously reported in the literature.
%
For instance, we use 0.5 seconds as the \textit{hello time} for \textit{MPR},  \textit{ProbFlood} and \textit{CDS-based}.
%
In the case of \textit{ABBA}, we use 0.3 seconds as the maximum waiting time.
%
Finally, for \textit{ProbFlood} we assign the values $k=15$ and $\sigma=1$.

\noindent
\textbf{Simulation time.}
%\subsection*{Simulation time}
As mentioned in Section~\ref{sec:background}, some algorithms build a topology to drive the broadcast operation.
%
To guarantee that the first broadcast message is properly handled by all protocols, we set an initial warm-up period of 5 seconds\deleted{before the first message is broadcast}.
The warm-up phase is used to create the initial topology in CDS-based algorithms.
%
%This time is used by  protocols can use to create any initial structure.
Likewise, \deleted{in our evaluation,} we stop each experiment a fixed amount of time (5 seconds) after the beginning of the last broadcast operation.
%
This grace period allows the last message to reach all nodes.
%
The total simulation time is then $10 + {\delta t} \times M$, where ${\delta t}$ is the interval between broadcast messages and $M$ is the number of scheduled messages.
