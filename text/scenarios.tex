\section{Experimental Scenario}
\label{sec:scenarios}

%
Our experiments are inspired by a real life scenario: a physical and spontaneous \emph{demonstration} gathering where the infrastructure for mobile communication is not able to serve the amount of clients and where individuals use their mobile phones in an ad-hoc mode to communicate.
%
In this scenario, the efficient dissemination of some messages to all participants is critical.
%
To simulate this kind of scenario, we must consider two parameters that influence the performance of broadcast in MANETs: \textit{network density} and \textit{nodes mobility}.
%
%Furthermore, we are interested in proposing a benchmark to evaluate the performance of broadcast protocols.
%
In the following, we describe the simulation environment and the parameters used in our study.

\subsection*{Simulation tool}

For our performance comparison study, we rely on INET3.3/OMNET++4.6, a simulation framework specifically aimed at evaluating networking algorithms~\cite{Varga:2008:OOS:1416222.1416290}.
%
This tool provides models for many protocols of the network stack such as 802.11g wireless communication~\cite{10.4108/ICST.SIMUTOOLS2009.5585}.
%
In addition, it contains models to describe and deal with mobility and energy consumption aspects.
%

\subsection*{Communication Scenario}

%
In a \textit{demonstration} scenario, some attendees have mobile devices with IEEE 802.11 capability.
%
Participants use such devices to broadcast messages using a MANET and they might attempt to do so at nearly the same time.
%
The messages to broadcast are usually \textit{short} because most of them are generated using the input capabilities of mobile devices.
%

To simulate these conditions,  we set the number of broadcast messages to \nrMessages{} and the interval between messages to $0.5$ seconds in our experiments.
%
In addition, the source of each message is randomly selected during the generation of the network (see next subsection).
%
Finally, the content of each message is randomly generated, unique and with a length of 32 bytes at most. 
%
%These two values allow us to evaluate the protocols under heavy and light network load.
%

\subsection*{Node Density}

We are interested in generating scenarios with different node density, this allows us to simulate more accurately the \textit{demostration} use case.
%
%In particular, the density in the vicinity of each node must equal a given value plus/minus a threshold.
%
To characterize the node density we use three parameters: transmission range, map size and number of nodes.
%
As shown in~\cite{Penrose2003}, there is a dependency between these parameters that  allows us to build network topologies with a given density by using random geometric graphs.
%

In our experiments, all nodes have a transmission range of 20~meters.~\footnote{Theoretically, IEEE 802.11 devices allow communication in a range between 20 and 140 meters depending on the line of sight.
Previous empirical tests show that it can effectively be between 20 and 30 m in indoor or crowded places~\cite{Garbinato2010}.}
Meanwhile the number of nodes is fixed to \nodesNumber{}, the mode reported by previous studies on the size of demonstrations in Western Europe~\cite{kriesi1995new}.
%
To create a network with a given node density, we use the values of transmission range and number of node to compute the map size using the aforementioned dependency relationship.
%
Then, we generate a laying on a square map by using a procedure based on random geometric graphs.
%
The output of this procedure is a network topology with the desired density.
%

Table~\ref{tbl:densisty-parameters} summarizes the simulations parameters we use to configure the density.
%
We instantiate \densitiesNumber{} networks of \nodesNumber{} nodes each and set the densities to  5,10,15,20,25,30,35 and 40, a range of values that is frequently found in the literature.

\begin{table}[ht]
	\footnotesize
	\centering
	
	\begin{tabular}{ll}
		\textbf{Parameter} & \textbf{Setting} \\
		
		\midrule
		Number of Nodes & \nodesNumber \\
		Transmission Range & 20 m \\
		Densities & 5--40 \\
		Map Size for smallest density & 354 m x 354 m \\
		Map Size for largest density & 125 m x 125 m \\
	\end{tabular}
	
	\caption{Simulations parameters affecting node density.}
	\label{tbl:densisty-parameters}
\end{table}

\subsection*{Mobility}

In our evaluation, we use the \textit{truncated-levy walk} (LW) mobility model, as it characterizes the mobility traces of humans carrying wireless devices~\cite{Rhee:2011}.
%
This model generates traces composed of frequent short walks and occasional long rides to distant locations.
%
In our experiments, we define two kind of scenarios: one without mobility (\textit{static}) and another with mobility at walking speed (\textit{dynamic}).
%
The generation of \textit{static} scenarios was presented in the previous subsection.
%
To generate \textit{dynamic} scenarios, we begin with a \textit{static one}.
%
Then, we use the LW model to generate mobility traces for each node.
%
The parameters of the LW model are set in such a way that the average node speed is close to $1.4$ $m/s$, a value reported in the literature~\cite{Browning390} as an estimation of the preferred walking speed.
%
To do so, we use the following values to feed the mobility model:

\begin{table}[ht]
	\footnotesize
	\centering
	
	\begin{tabular}{lcp{3.5cm}}
		\textbf{Parameter} & \textbf{Value} & \textbf{Description} \\
		
		\midrule
		FL\_EXP & -3.9 & Exponent of the flight length distribution \\
		FL\_MAX & 50 & Maximum value of the flight length distribution \\
		WT\_EXP & -1.8 & Exponent of the waiting time distribution \\
		WT\_MAX & 100 & Maximum value of the waiting time distribution \\
	\end{tabular}
	
	\caption{Configuration of the LW mobility model.}
	\label{tbl:mobility-parameters}
\end{table}

Afterwards, we perform several checks on the traces to guarantee that: i) the average speeds are indeed close to $1.4$ $m/s$, ii) the node density is the desired one during all the simulation time, and iii) the topology remains connected all the time.~\footnote{Except for a very low density (5) where we are unable to generate a topology that remained connected during all the experiments.}

\subsection*{Energy Consumption}

Efficient energy utilization in wireless communication must be taken into consideration.
%
Since power consumption highly depends on the Wi-Fi chip used by mobile devices, we chose to model power consumption using the specifications of an actual chip found in modern mobile devices to feed the simulator.
%
The Broadcom BCM4329~\cite{BCM4329} can be found in many modern devices because it supports the protocol Wi-Fi 802.11g on the 2.4 GHz frequency band.
%
Table~\ref{tbl:wifi-chip} shows the amount of energy that this chip requires in its different operation modes.
%
This information is used in setting the power consumption model of INET.

\begin{table}[ht]
	\footnotesize
	\centering
	
	\begin{tabular}{lr}
		\textbf{Mode} & \textbf{Consumption} \\
		
		\midrule
		%Off	  & nW & 57.6 \\
		Sleep  & 648 nW \\
		Receiver Listen & 244.8 mW \\
		Receiver Active (RX) & 295.2 mW \\
		Transmitter Active (TX) & 1206 mW \\
	\end{tabular}
	
	\caption{Power consumption per mode of the Broadcom BCM4329 Wi-Fi chip.}
	\label{tbl:wifi-chip}
\end{table}

To simulate this chip, we use the \textit{StateBasedEnergyConsumer} model provided by INET.
%
This model measures how many Joules were consumed based on the time the chip spends on each mode (as described in Table~\ref{tbl:wifi-chip}).
%
Formally, this energy consumption model uses three functions: $c : M \mapsto \mathbb{R} $, $r_m: \mathbb{R} \mapsto M$ and $t_m: \mathbb{R} \mapsto M$ where $M$ is the set of operation modes of the chip, $c$ is the consumption of the chip on each mode, and functions $r_m, t_m$ map from simulation time to operation modes of the \textit{receiver} and \textit{transceiver}, respectively.
%
INET then computes the energy consumption $C(t)$ using:  $C(t)=\int_{0}^{t_\textit{simulation}} (r_m \circ c) (t) + (t_m \circ c) (t) \textit{dt}$.
%
The function $m$ is given and INET computes both $r_m$ and $t_m$ during the simulation.



\subsection*{Algorithm specific parameters}

The behavior of each protocol depends on the values of its parameters.
%
To configure these parameters in a meaningful way, we choose values previously reported in the literature.
%
For instance, we use 0.5 seconds as the \textit{hello time} for both \textit{MPR} and \textit{node-degree-based} CDS.
%
In the case of \textit{ABBA}, we use 0.3 seconds as the maximum waiting time.
%
Finally, for \textit{ProbFlood} we assign the values $k=15$, $\sigma=1$, and $\textit{hello time} = 0.5$.


\subsection*{Warm-up period}
Since some algorithms build a topology to drive the broadcast operation, there is a warm-up period before the first message is broadcast that protocols can use to create any initial structure.
%
Finally, in our evaluation we stop each experiment a fixed amount of time after the beginning of the last flooding operation.
